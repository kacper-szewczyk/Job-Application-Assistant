# 0026 — LinkedIn import through the Member Data Portability API

- **Status:** Accepted
- **Date:** 2026-10-15
- **Issue:** #72 (from the T20 research, #21)
- **Amends:** the "never ask for LinkedIn tokens" rule (SPEC §5, CLAUDE.md, ADR 0010, ADR 0020)

## Context
The data archive (ADR 0010) can take a day to arrive, and the user has to request it again for every update. Under the EU Digital Markets Act, LinkedIn offers EEA and Swiss members a self-serve *Member Data Portability API (Member)*. The member creates a developer app on LinkedIn's default "Member Data Portability (Member) Default Company" page, adds the product, and generates a token for their own data in the OAuth Token Generator. The token lasts about 60 days and has no refresh token. `GET https://api.linkedin.com/rest/memberSnapshotData?q=criteria&domain=…` with `Linkedin-Version: 202312` (the only accepted version) returns one domain per call, paged by `start`, until LinkedIn answers 404 "No data found for this memberId". Rows use the archive CSVs' column labels. Called without `domain`, it returns every domain, including messages, connections, logins and ads data.

Until now the rules said jaa never asks for LinkedIn tokens. The rule exists so that jaa never acts as the member on LinkedIn and never holds a credential it could leak. This API is read-only, reaches only the member's own data, and is meant for exactly this use. The user approved a narrow exception in #21.

## Decision
- **One command, the user's own terminal.** `jaa import linkedin-api` asks for the token at a hidden prompt (`--how` prints the steps for getting one). It refuses to run when stdin is not a terminal, and there is no argument, option, environment variable or config key for the token, so it cannot be piped in, scripted or put in shell history. The command is user-only in the skill and denied to Claude in `.claude/settings.json` (ADR 0020). The MCP server has no LinkedIn API tool, and its instructions tell Claude never to take a token in the chat.
- **The token is used once and kept nowhere.** It is validated as URL-safe text (an error never repeats what was pasted), wrapped in `jaa.logging.Sensitive`, and sent only in the Authorization header to `api.linkedin.com` over https. It is never written to the database, the import run, exports, logs or error messages, and errors from the transport carry no request details (`raise … from None`). The CLI drops its reference once the pull ends. Tests check that the token appears in no output, log line, database file or export.
- **Only mapped domains, one per request.** Profile: `PROFILE`, `EMAIL_ADDRESSES`, `PHONE_NUMBERS`, `POSITIONS`, `EDUCATION`, `SKILLS`, `LANGUAGES`, `CERTIFICATIONS`, and since #91 (ADR 0032) `PROJECTS`, `VOLUNTEERING_EXPERIENCES`, `PUBLICATIONS`, `PATENTS`, `HONORS`, `COURSES`. Jobs: `SAVED_JOBS`, `JOB_APPLICATIONS`, `SAVED_JOB_ALERTS`, `JOB_SEEKER_PREFERENCES`. jaa never makes the all-domains call. The sections the archive importer does not import yet (projects, honors, courses, publications, patents, volunteering) are not requested either. They are added here when the parser learns them, so jaa never downloads data it then drops (done in #91, ADR 0032). The issue listed them, and this is the one deviation from its scope. Email and phone domains are requested because the archive import uses the same files.
- **Paging and limits.** Pages are read until LinkedIn's "No data found" 404, as LinkedIn's docs require (its `total` is not reliable). That 404 on the first page means the domain is empty, or not prepared yet right after consent. It is reported as a note, not an error. Caps: 50 pages per domain (beyond that the run is `partial` with `too_many_pages`), 300 requests per import, and 10 MB per response. 401 (expired or revoked token), 403 (no product access), 426 (version), 429 (rate limit), any other status, a redirect off `api.linkedin.com`, or a body that is not the documented JSON stops the import with nothing stored.
- **Profile values go through the archive parser.** `jaa.importers.linkedin.parse_linkedin_tables` takes rows that did not come from CSV files (`RowTable`, keyed by the archive file they match). They get the same required-column checks, the same data minimization and the same field keys as ADR 0010, so an archive import and an API import meet on the same keys. Identical values are skipped and different values go to review. Facts are `unreviewed`, with provenance `LinkedIn <DOMAIN> row N`.
- **Import run.** New `ImportSourceType.LINKEDIN_API` (migration 0013). `source_path` is empty and `source_sha256` hashes the profile domains' rows, so an identical re-import names the earlier run. Retention is `keep`, as for pasted text: nothing was written to disk, so there is no source file to delete. The summary holds per-domain row counts, empty domains and job counts, never values.
- **Migration 0013 rebuilds `import_runs`**, because SQLite cannot change a CHECK constraint in place. `migrate` now runs migrations with foreign keys off and runs `PRAGMA foreign_key_check` before each commit, following SQLite's documented procedure for rebuilding a table, so dropping the old table cannot null `profile_facts.import_run_id`. A migration that leaves broken references is rolled back.
- **Job data is the user's to act on.**
  - Saved jobs with a link become `manual` jobs (ADR 0023) with title, company and the LinkedIn link, after a confirmation prompt (or `--add-saved-jobs/--no-saved-jobs`). The link is never fetched. Links already added by hand are skipped, and saved jobs without a link are counted, not added. LinkedIn sends no descriptions, so these jobs have nothing to match until the user pastes one.
  - Applications are listed with the jobs in jaa that may be the same one (same link, or same company and title). jaa records nothing: the user runs `jaa apply` themselves (SPEC: the user submits applications).
  - Job alerts and job seeker preferences are shown as suggestions for searches and `jaa onboard`, and are never stored. Only the preference labels jaa can use are shown; the phone number, commute address and similar fields are dropped. Contact details and the questions and answers in applications are never shown.

## Consequences
- The rule now reads: jaa never asks for LinkedIn passwords or cookies, and accepts a token only at `jaa import linkedin-api`'s hidden prompt. CLAUDE.md, the skill and the MCP server instructions say so.
- The command works only for EEA and Swiss members; everyone else uses the archive.
- LinkedIn's docs name the self-serve scope differently in different places (`r_dma_portability_self_serve` in the research, `r_dma_portability_member` on the Snapshot API page). jaa never names or checks the scope: the member generates whatever the Token Generator offers for the product, and LinkedIn's 403 tells them if it is wrong.
- The fixtures are synthetic and follow LinkedIn's documented sample. The command has not yet been run against the live API. LinkedIn's labels for the job domains are not documented, so they are taken from the archive files and could differ. Unknown labels are ignored and a missing required one is reported as `unexpected_format`.
- jaa has no way yet to add a description to a job that has none (saved jobs, or `jaa jobs add` without one). That is a follow-up.
